pg_lake 全景架构与端到端流程

面向零数据库基础：从文件与表开始，逐步理解检索、I/U/D、快速 MOR、Iceberg、Catalog、OLTP 与 Lance。

控制面：PostgreSQL

  • 用户只需要连接 PostgreSQL。
  • pg_lake_table 决定全量或局部下推。
  • PostgreSQL 快照保证目录读取一致性。
  • 不支持下推的逻辑仍可在 PostgreSQL 执行。

执行面：DuckDB

  • pgduck_server 是独立进程，不嵌入 backend。
  • PostgreSQL 通过 libpq 和 Unix socket 发送 SQL。
  • DuckDB 执行列式扫描、聚合、连接和文件写入。
  • duckdb_pglake 补足兼容函数与文件系统能力。

表格式：Iceberg

  • Iceberg 组织 metadata、snapshot、manifest 和文件。
  • Catalog 指向当前 metadata，是提交协调点。
  • Position delete 支持 Merge-on-Read。
  • 外部引擎可通过相同表格式读取数据。

关键工程边界

  • PostgreSQL 事务不等于对象存储的原子事务。
  • 写数据文件和切换 metadata pointer 必须协调。
  • Catalog、缓存、凭证和远端 I/O 都需独立观测。
  • 性能收益来自文件裁剪与向量化下推。

01
First principles

pg_lake 整体架构到底是什么？

它不是“另造一个数据库”，而是把 PostgreSQL、DuckDB、Iceberg 和对象存储拼成一个湖仓系统。每一层只做自己擅长的事情，再由 pg_lake 承担跨层协调。

一句话：你继续用 PostgreSQL 写 SQL；pg_lake 把适合的工作交给 DuckDB；Iceberg 记录哪些文件组成当前表；对象存储保存真正的数据文件。

PostgreSQL 仍是门面

客户端、SQL 语法、权限、事务入口和结果类型都保持 PostgreSQL 使用体验。

DuckDB 是执行加速器

它负责适合列式向量化的大批量文件计算，但不拥有最终事务状态。

Iceberg 是共享契约

它让多个引擎对“当前表由哪些文件组成”达成一致，而不是替代数据库执行引擎。

02
Core vocabulary

文件格式和表格式是什么概念？

这是理解 Iceberg 的第一道门槛。Parquet 解决“一份文件怎样存得紧凑、读得快”，Iceberg 解决“许多文件怎样长期组成一张可修改、可追踪的表”。

类比：文件格式像“每一本书的印刷装订标准”；表格式像“图书馆如何登记全部书、版本、下架记录和最新目录”。

Parquet 不等于 Iceberg

Parquet 可以单独存在；Iceberg 表通常引用许多 Parquet 文件，并额外管理版本、删除和演化。

表格式不负责算 SQL

Iceberg 提供元数据契约。真正扫描、过滤和聚合文件的是 DuckDB、Spark、Trino 等引擎。

pg_lake 同时跨两层

写文件时遵守 Parquet；提交表状态时遵守 Iceberg；入口和事务语义来自 PostgreSQL。

03
Read path

一次 SELECT 检索从头到尾怎么走？

查询并不是 PostgreSQL 收到 SQL 后立刻让 DuckDB 扫所有文件。pg_lake 先规划下推，再在执行开始时绑定事务快照、找到真正需要的文件并做裁剪。

关键思想：先用 PostgreSQL 的语义和事务视角决定“查什么”，再用 Iceberg 元数据缩小“查哪些文件”，最后让 DuckDB 高速执行“怎样查”。

01 Parser识别 SQL、类型、权限和表。
02 Planner判断整条或局部查询能否交给 DuckDB。
03 Snapshot用 PostgreSQL 事务快照固定可见元数据。
04 Pruning按分区和列统计跳过不相关文件。
05 ExecuteDuckDB 执行 read_parquet 与下推算子。
06 Return结果转换为 PostgreSQL tuple 返回。
有 position delete 时，DuckDB 还要读取文件名和行号，并用 (file_path, pos) 反连接过滤已删除行；这就是 MOR 的读时合并成本。
04
Write path

INSERT / UPDATE / DELETE 端到端怎么走？

湖表中的数据文件通常是不可变的，因此修改一行并不是“原地改几个字节”。pg_lake 把修改转换为新增数据文件、删除文件或替换文件，再提交新的 Iceberg 表版本。

最重要的等式：UPDATE = DELETE 旧行 + INSERT 新行；小范围 DELETE 通常写 position delete，大范围 DELETE 倾向重写数据文件。

INSERT 为什么简单

它只需要生成新的不可变数据文件，并把文件加入新的表版本，不需要改旧文件。

UPDATE 为什么更贵

它同时包含旧行删除和新行追加，需要保持两部分在同一事务版本里一起可见。

TRUNCATE 是什么

它可以直接从新表版本中移除全部数据文件引用，而不必逐行扫描和删除。

05
Merge-on-Read

pg_lake 怎么实现快速 MOR？

MOR 的目标是让小范围 UPDATE/DELETE 不重写大 Parquet 文件。写入时只记录“哪一行已删除”，读取时再把数据文件和删除文件合并，后台通过 VACUUM 控制长期成本。

不是免费加速：MOR 把成本从“每次写都重写大文件”移动到“读时过滤 + 之后压实”。它适合少量修改，不适合无限积累删除文件。

为什么写得快

只写很小的 position delete 文件，避免为删除几行复制整个大 Parquet 文件。

为什么读还能快

删除合并被下推到 DuckDB 的向量化 Parquet 扫描，并且只有需要时才附加行号。

为什么仍需 VACUUM

delete files 越多，读取和元数据规划越重；压实把逻辑删除重新物化成干净数据文件。

阈值是策略而不是 Iceberg 规范：默认 20% 和 10,000,000 行来自当前 pg_lake 实现，可通过 GUC 调整。真正合适的值取决于文件大小、更新比例、读写比和 VACUUM 周期。
06
Capability boundary

pg_lake 用到了 Iceberg 哪些能力？Iceberg 的能力范围到哪里？

Iceberg 是开放表格式，提供“怎样描述和提交一张湖表”的标准。pg_lake 使用这些标准元数据，但 SQL、事务接入、查询下推、写入策略和运维仍由 PostgreSQL 与 pg_lake 实现。

职责边界：Iceberg 保证不同引擎能理解同一张表的结构和版本；pg_lake 负责让 PostgreSQL 用户真正能创建、查询、修改和维护这张表。

规范能力

Snapshot、Manifest、字段 ID、分区演化、delete file 和 metadata pointer 都来自 Iceberg 契约。

pg_lake 增值能力

SQL 接入、事务 Hook、DuckDB 下推、文件裁剪、写入策略和维护调度由 pg_lake 完成。

不要过度承诺

Iceberg 不是 SQL 引擎、不是权限系统，也不是适合高并发点更新的 OLTP 行存储。

07
Counterfactual

如果没有 Iceberg，会怎么样？

pg_lake 仍可以让 PostgreSQL 通过 DuckDB 读取和写入 Parquet、CSV、JSON，但它会从“湖仓表系统”退化成“文件访问与加速层”。缺少的是长期正确管理一张表的共同标准。

本质变化：还能查文件，不再天然知道“哪些文件是当前表、怎样并发提交新版本、外部引擎如何发现同一张表”。

还保留什么

PostgreSQL FDW、DuckDB 文件扫描、COPY 和普通 Parquet/CSV/JSON 读写仍然可以存在。

真正失去什么

标准化版本、提交、演化、删除、发现和跨引擎共享能力，而不仅仅是几个 JSON 文件。

替代代价

所有缺失能力都要变成 pg_lake 私有协议，测试、恢复和生态兼容成本都会上升。

08
Table discovery and commit

Catalog 是做什么的？为什么需要 Catalog？

Iceberg 每次提交都会产生一个新的 metadata.json，旧文件不会被原地覆盖。Catalog 保存“逻辑表名当前指向哪个 metadata.json”，同时提供原子切换和冲突检测。

类比：对象存储里可能有很多版目录；Catalog 是图书馆门口唯一的“当前目录指示牌”，读者按它找最新版，写者只能原子地把指示牌从旧版换到新版。

表发现

外部引擎通过逻辑表名找到当前 metadata，而不用猜对象存储中哪个 JSON 最新。

原子提交

先写不可变文件，最后只原子切换一个指针；读者要么看到旧版本，要么看到新版本。

并发冲突

两个写者都从旧版本开始时，只有一个能先切换指针，另一个必须重新规划。

对象存储中的“最后修改时间最新”不能替代 Catalog。时钟、并发写入、重试和孤儿文件都会让“猜最新文件”失去可靠性。
09
Catalog responsibilities

pg_lake 承担了哪些 Catalog 能力？

pg_lake 既维护 PostgreSQL 内部的表与文件状态，也能桥接 Iceberg REST Catalog 和对象存储 catalog.json；同时把 metadata 变更绑定到 PostgreSQL 事务 Hook。

不是单一组件：pg_lake 的 Catalog 能力分散在本地系统表、兼容视图、REST/Object-store 适配、检查函数和事务提交协调中。

内部表

pg_lake 既保存 metadata pointer，也维护执行所需的文件、统计、分区和删除映射。

外部表

可以通过 REST Catalog 或 object-store catalog 获取当前 metadata location。

事务边界最复杂

本地 Catalog、对象存储文件和外部 REST 提交不在同一个物理事务中，必须分阶段协调。

10
Workload fit

pg_lake / Iceberg 和 OLTP 数据库有什么区别？

两者都能通过 SQL 修改数据，但物理机制和优化目标完全不同。OLTP 为大量短小、并发、点查点改事务设计；pg_lake/Iceberg 为对象存储上的大规模分析和开放互操作设计。

不要把它当替代品：pg_lake 可以继承 PostgreSQL 事务入口，但湖表文件并不会因此变成适合高频逐行更新的 Heap + WAL + Index 存储。

OLTP 优化目标

低延迟点查、短事务、高并发更新、强索引和崩溃恢复。

Lakehouse 优化目标

大批量列式扫描、对象存储成本、开放文件和多计算引擎共享。

pg_lake 的价值

让用户保留 PostgreSQL SQL/事务入口，同时把分析数据放进开放湖表。

11
Format choice

pg_lake / Iceberg 和 Lance 有什么区别？

二者都面向数据湖，但优化中心不同。Iceberg 强调开放表管理、计算引擎互操作和超大分析表；Lance 同时定义原生文件/表/索引能力，强调随机访问、AI/ML 数据和向量工作流。

选择方向：通用湖仓互操作和 SQL 分析优先研究 Iceberg；向量、Embedding、多模态样本和随机访问优先单独评估 Lance；两者都不是 OLTP 数据库替代品。

Iceberg 关注点

跨引擎表状态、快照、文件规划、演化和 Catalog 提交，底层数据常为 Parquet。

Lance 关注点

原生文件/表/索引栈，强调随机访问、向量与 AI/ML 数据生命周期。

共同边界

二者都是湖上技术，不应直接替代成熟 OLTP 存储引擎的行级事务和索引能力。
